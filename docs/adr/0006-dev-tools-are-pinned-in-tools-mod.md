# Dev tools are pinned in tools.mod, run with go tool

goose, sqlc, templ and staticcheck are declared with the Go `tool` directive in a separate `tools.mod` and run as `go tool -modfile=tools.mod <name>`, through the `TOOLS` variable of the Taskfile. `go install ...@latest` was rejected: each machine, the sandbox, CI and the `migrate` image would get whatever was latest on the day, so `sqlc diff` could pass locally and fail in CI. Pinning is the same in `go.mod` and in `tools.mod`; the separate file is about the module graph: the tools' transitive dependencies stay out of the application's `go.mod` and `go.sum`, and cannot raise the version of a dependency the application ships. Two costs follow. `go mod tidy` does not apply to `tools.mod`, because it reads the application's packages as imports of an external module and would add the repository itself to `require`; `go get -tool` keeps the file consistent. And the templ CLI lives in `tools.mod` while the templ library will live in `go.mod`, so the two versions must be chosen together when the library is first added.
