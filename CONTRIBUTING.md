# Contributing

One person writes the code, so this is a convention to keep the history
readable, not a process to negotiate. For how the owner and Claude share the
work, see [CLAUDE.md](CLAUDE.md).

## Branches

- `main` is always the last good state. Nothing is committed to it directly
  once CI exists (S4); until then, keep it green by hand.
- `scaffold` is a read-only reference: an earlier implementation to compare
  against after a task is done. Never merge it, never commit to it.
- One branch per issue, named `<type>/<name>_<id>` where the type is
  `feature`, `fix` or `chore`, the name is the issue title in short snake_case
  and the id is the issue number, for example `feature/go_skeleton_5` or
  `chore/git_hygiene_1`. Scaffolding and design issues use `chore`.

## Pull requests

- One pull request per issue, opened against `main`.
- The description says `Closes #<n>` so the issue closes on merge.
- The checklist of the issue (acceptance criteria, definition of done) is the
  review checklist. Tick it in the issue, not in the pull request.
- Merge with **squash**: one commit on `main` per issue, titled after the issue.
  The branch history is working notes and is not kept.
- Delete the branch after merging.

## Commits

- English, imperative mood, subject line under about 70 characters
  ("Add health endpoint", not "Added" or "Adds").
- A body only when the *why* is not obvious from the diff.
- Inside a branch, commit as often as is useful; the squash tidies up.

## Checks

- `task init` once after cloning: it creates `.env` and installs the Git hooks.
- `task check` runs what CI runs. The `pre-commit` and `pre-push` hooks run a
  subset of it, can be skipped with `--no-verify`, and never replace CI. See
  the Git hooks section of the [README](README.md).
- There is no `commit-msg` hook: the commit format above is a convention, not
  something to enforce. Branch commits are working notes, and only the title of
  the squashed commit survives.

## Continuous integration

[`ci.yml`](.github/workflows/ci.yml) runs on every pull request and on every push
to `main`, as one job, `quality`. It drives the same Task targets as `task check`:

1. `task lint` (`go vet`, staticcheck)
2. `task init:env` and `task up` start Postgres, only if a migration exists
3. `task migrate`, only if a migration exists
4. `task test`
5. `task check:sqlc`, only if `sqlc.yaml` exists
6. `task check:templ`, only if a `.templ` file exists

The conditional steps use `hashFiles(...)`, so they switch on by themselves when
their input is added; a skipped step is grey, not green. A new push to the same
branch cancels the running pull request run, never a run on `main`. The reasons
for one job with conditional steps are in
[ADR 0007](docs/adr/0007-ci-is-one-job-with-conditional-steps.md).

## Documentation

- The spec, `docs/design.md`, `CONTEXT.md` and the ADRs are the source of
  truth. A pull request that changes a decision updates them in the same
  change, so the code never diverges silently.
- A decision that is hard to reverse and surprising gets an ADR in `docs/adr/`.

## Files

- [`.editorconfig`](.editorconfig) sets indentation and line endings: tabs for
  Go and templ, LF everywhere. Use an editor that honours it.
- Generated code is not committed while it can be regenerated cheaply
  (`*_templ.go` is ignored). Code generated by sqlc is committed and checked in
  CI (`sqlc diff`) once T4 has landed.
- Nothing local is tracked: `.env`, IDE folders, `.claude/settings.local.json`.
  `.claude/agents`, `.claude/skills` and `.claude/output-styles` are shared.
